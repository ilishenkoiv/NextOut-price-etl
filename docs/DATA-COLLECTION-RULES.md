# DATA-COLLECTION-RULES — канонический план сбора данных NextOut

Статус: **Stage 0 — только документация.** Дата фиксации: 2026-09-21.

Этот файл фиксирует согласованную владельцем целевую архитектуру сбора данных и отделяет её от
**фактического текущего поведения кода** на 2026-09-21. Файл ничего не меняет в коде, workflow,
cron, переменных GitHub, БД, secrets, расписании или production. Реальные сборы и API-запросы на
этом шаге не запускались.

Правила чтения этого документа:
- Раздел «ЦЕЛЬ» — согласованная архитектура, к которой идём.
- Раздел «СЕЙЧАС» — что фактически делает код в репозитории на дату фиксации (проверено по
  исходникам, ссылки на файлы приведены).
- Раздел «ОТКРЫТО» — расхождения цели и факта, ещё не реализованные пункты.
- Ничего из «ЦЕЛЬ» не считается сделанным, пока это не доказано тестом и не отмечено отдельной
  датированной записью. Журнал только дополняется (см. `ПРАВИЛА.md`, «18.09 — журнал только
  дополняется»).

Ссылки на исходники (все в этом репозитории `.work/expansion48-data-readiness`):
`scripts/collection-schedule.mjs`, `scripts/run-collection.mjs`, `scripts/collection-adapters.mjs`,
`scripts/collection-planning.mjs`, `scripts/snapshot-daily-origin-cheapest.mjs`,
`scripts/refresh-roulette-prices.mjs`, `scripts/fetch-window-prices.mjs`,

## 0. Инварианты (действуют на всех этапах, не подлежат нарушению)

Эти правила уже закреплены в `ПРАВИЛА.md` и в коде; здесь они собраны как единый список,
потому что любой этап плана обязан их сохранять.

1. **Один токен, строго последовательно.** Все обращения к API партнёра используют один
   `TP_TOKEN` и выполняются только последовательно. Параллельные запросы недопустимы даже при
   отсутствии отказов по частоте. (`ПРАВИЛА.md` 16.09; concurrency `nextout-data-collection`,
   `queue: max`, `cancel-in-progress: false` во всех workflow.)
2. **Темп ≤ 80 % лимита партнёра.** Ориентир v3/prices_for_dates: 600 запросов/мин → цель
   480/мин → пауза 125 мс (`refresh-roulette-prices.mjs` `INTERVAL_MS=125`,
   `fetch-window-prices.mjs`). При более низком лимите в заголовке ответа — замедляться до 80 %
   от него.
3. **Нет выдуманных цен.** Отказ / ошибка / пустой, но успешный ответ никогда не затирает
   известную цену. Место без собранной цены показывает «цену/отель проверить», без Total и без
   бюджетного вердикта. (`ПРАВИЛА.md` 21.09 «Критерий допуска»; `fetch-window-prices.mjs` «RULES
   THAT MUST HOLD»; `refresh-roulette-prices.mjs` — HTTP/сеть/битый ответ сохраняют прежнюю цену.)
4. **Маршрут никогда не удаляется из каталога.** Отсутствие цены не удаляет город. (`ПРАВИЛА.md`
   15.09 «направления и проверка даты заселения», 16.09.)
5. **Обе цены собираются безусловно** по каждому направлению и месяцу: самая дешёвая прямая и
   самая дешёвая с пересадками; второй запрос делается всегда. Показывается меньшее из двух с
   пометкой. (`ПРАВИЛА.md` 18.09 «цена с пересадкой не запасная».)
6. **Явный market по аэропорту вылета.** Market выводится только из origin, неизвестный origin
   падает закрыто. (`src/data/origin-markets.js`, README «market provenance».)
7. **Идемпотентность и checkpoint.** Каждая единица работы ограничена по времени, коммитит строки
   до продвижения курсора, переживает смену runner, полночь и пропущенные слоты. `save()`
   огорожен lease; потеря lease останавливает воркер. (`collection-schedule.mjs`.)
8. **Нет двойного владельца очереди.** Один writer на очередь `nextout-data-collection`. Legacy и
   coordinator не должны собирать одновременно; гейт — переменная `COLLECTION_MODE`.
9. **Production-БД, миграции и secrets — только вручную владельцем.** Агент не применяет миграции,
   не меняет переменные/секреты GitHub, не запускает production-сбор без явного разрешения.
   Секреты никогда не печатаются/логируются (`run-collection.mjs` redaction).
10. **Пагинация.** Любой `.select()` к таблице, способной превысить 1000 строк, — через `.range()`
    с обязательным `.order()` по уникальному ключу (`CLAUDE.md` основного репозитория; здесь —
    `load()` в `collection-adapters.mjs`, циклы `PAGE=1000`).
11. **Погода, фото, отели — отдельные процессы**, не смешиваются с MAIN (см. §9).

## 1. Основной сбор авиабилетов (MAIN)

### ЦЕЛЬ
- 184 пользовательских места; 182 flight IATA = 139 старых + 43 новых.
- Единица работы: `origin × destination × month`. Горизонт: 6 месяцев.
- MAIN работает через durable checkpoint и idempotent commit.
- 43 новых IATA получают ограниченную (bounded) Expansion-транш; транш front-loaded, но не
  вытесняет остальной проход целиком.
- Полный логический проход MAIN — не более 24 часов, желательно ~12 часов.
- Планировщик перераспределить так, чтобы MAIN получал ~180–210 минут из 235-минутной сессии,
  сохранив FAST, TAIL, maintenance, checkpoint, stop/yield и lease.

### СЕЙЧАС (2026-09-21)
- Coordinator запускается по cron `7 */4 * * *` (каждые 4 часа), сессия
  `COLLECTION_SESSION_MINUTES=235` (`collection-coordinator.yml`, `run-collection.mjs`).
- Внутренний цикл планировщика — **120 минут** (`CYCLE_MS`), не 30. Слоты в каждом 120-мин цикле
  (`collection-schedule.mjs` `SLOTS`):

  | Слот | Минуты в цикле | Длительность |
  |---|---|---|
  | fast | 0–10 | 10 |
  | maintenance | 10–15 | 5 |
  | main | 15–45 | 30 |
  | tail | 45–65 | 20 |
  | maintenance | 65–70 | 5 |
  | main | 70–95 | 25 |
  | tail | 95–110 | 15 |
  | reserve | 110–120 | 10 |

  Итого на 120 мин: **main 55, tail 35, fast 10, maintenance 10, reserve 10.**
- За 235-мин сессию (~1.96 цикла) на MAIN приходится ≈ **55 × 1.96 ≈ 108 минут** полезного
  времени — это совпадает с наблюдаемым bottleneck (~108 мин MAIN из 235-мин сессии).
- Пустой/завершённый слот отдаёт остаток времени последующим фазам; reserve может докручивать
  любую задачу.
- `MAIN_CYCLE_MS = 24 ч` — один основной проход в сутки (строка для двух проходов/сутки
  закомментирована). Общий размер прохода ~13.5k ячеек `route×month`, ~2–3k коммитится за сессию,
  поэтому `done` MAIN достигается раз в ~1.5–2 суток — **это и есть текущая фактическая
  длительность полного прохода**.
- `mainAtRisk()` + `guaranteeDailyMain` (по умолчанию **OFF**) позволяют слоту tail уступать
  main, когда текущий проход рискует не уложиться в 24 ч. По умолчанию поведение legacy.
- Expansion: `EXPANSION_WAVE` поддерживает 0/10/21/43 новых аэропорта; незавершённый проход
  «пинит» свою волну (`run-collection.mjs`, `collection-adapters.mjs`, `collection-planning.mjs`
  `cellOrder` front-load транша; `EXPANSION_TRANCHE_DESTS`).

### ОТКРЫТО
- MAIN получает ~108 мин/сессию вместо целевых 180–210. Требуется перераспределение слотов
  (Stage 5) **без** удаления FAST/TAIL/maintenance/reserve и без потери checkpoint/lease/yield.
- Цель «полный проход ≤ 24 ч (желательно ~12 ч)» пока не достигается (~1.5–2 суток).

## 2. Маршруты без цены (dead / no-price)

### ЦЕЛЬ
- Маршрут никогда не удаляется из каталога.
- Маршрут без цены попадает в отдельный dead/no-price список.
- Полный сбор такого маршрута не выполняется каждый проход: за проход проверяется ~1/7 списка.
- Если цена снова появилась — маршрут возвращается в MAIN.
- **Подтверждённый порог:** маршрут считается устойчиво dead только после отсутствия цены не
  менее **30 дней**.
- Expansion-маршруты используют ту же dead/no-price логику, но не должны выпадать из bounded
  tranche из-за ошибочного раннего dead-статуса.

### СЕЙЧАС (2026-09-21)
- Каталог сохраняется полностью; отсутствие цены город не удаляет (инвариант §0.4).
- Логика «1/7 за проход» существует для хвоста каталога (`fetch-window-prices.mjs`: TOP_DESTS +
  ежедневная 1/7 доля; планирование в `collection-planning.mjs`).
- Проверка «жив ли маршрут» опирается на **текущий 6-месячный горизонт**.

### ОТКРЫТО
- **30-дневного порога подтверждённого dead-статуса в коде нет.** Текущая реализация судит о
  наличии цены только по текущему горизонту и не выдерживает 30 дней отсутствия перед пометкой
  dead. Это незакрытый пункт будущей реализации (Stage 6).
- Отдельный явный dead/no-price список как самостоятельная сущность (с датой первого «нет цены»)
  требует проектирования; сейчас статус выводится из наличия строк, а не из выделенного реестра.
- Требуется гарантия, что Expansion-маршрут не получает ранний dead-статус и остаётся в tranche.

## 3. Cheapest carousel (рулетка) — селекция и refresh строго раздельны

### ЦЕЛЬ
**A. Ночная selection — один раз в сутки** (`snapshot-daily-origin-cheapest.mjs`):
- выбирает до 10 уникальных направлений на каждый origin;
- меняет состав pool;
- **не** запускается каждые 30 минут.

**B. Price refresh — каждые 30 минут** (`refresh-roulette-prices.mjs`):
- не выбирает новые направления и не меняет состав pool;
- проверяет только уже выбранные билеты;
- ориентир: до 10 × 21 origin = до 210 билетов; **фактическое число API-запросов и разрез
  direct/any обязательно измерить (Stage 1)**;
- обязательны checkpoint и отсутствие параллельных запусков.

### СЕЙЧАС (2026-09-21)
- **Селекция** (`snapshot-daily-origin-cheapest.mjs`): `selectDailyCheapestPool` строит один
  глобальный pool на origin по offers, оставляет по одному самому дешёвому реальному билету на
  направление, до 10 рангов на origin. Неизвестные (ещё не готовые) направления не попадают в
  pool (`publishedSnapshotDestinations`, гейт `SNAPSHOT_EXPANSION_WAVE`, по умолчанию 0). Retention
  pool — 31 день.
- **Когда фактически публикуется pool:** (1) при завершении полного прохода MAIN — стадия
  `snapshot` в main-адаптере; (2) в конце каждой сессии, если полный MAIN за неё не завершился
  (`run-collection.mjs` `shouldPublishEndOfSession` / `publishEndOfSessionPool`). То есть pool
  может перестраиваться **несколько раз в сутки** (сессии идут каждые 4 ч), а не строго один раз
  ночью.
- **Refresh** реализован в двух местах:
  - как отдельный скрипт `refresh-roulette-prices.mjs` (checkpoint
    `roulette_price_refresh_checkpoint`, одна проверка на билет, обновление цены на месте,
    удаление только при успешном «билета больше нет», idle-gate priority 0);
  - и как turn 1 maintenance-адаптера в coordinated mode (`collection-adapters.mjs`): берёт
    последний pool, проверяет билеты порциями, коммитит через `collection_commit_roulette`,
    цикл привязан к 30-мин окну (`Math.floor(now/1800000)`).

### ОТКРЫТО
- Строгое разделение «селекция ровно один раз в сутки» не соблюдается: pool перестраивается по
  событиям MAIN/конца сессии. Нужно (Stage 2) развести ночную селекцию и частый refresh так,
  чтобы refresh никогда не менял состав/порядок/раскрытый билет пользователя.
- Число origins в pool («21») и фактическое количество API-запросов на один refresh, разрез
  direct/any — **не измерены**; подлежат измерению в Stage 1.

## 4. Weekend/holiday carousel — селекция и refresh строго раздельны

### ЦЕЛЬ
**A. Ночная selection — один раз в сутки:** один полный процесс выбирает лучшие варианты
выходных/праздников; состав выбранных окон сохраняется; selection не повторяется каждые 30 минут.

**B. Price refresh — каждые 30 минут:** проверяет только сохранённые направления и окна; не ищет
новые; работает частями через checkpoint. Полный исторический проход ~6 часов, поэтому полный
проход не запускается каждые 30 минут — нужен **инкрементальный refresh сохранённого набора**.

### СЕЙЧАС (2026-09-21)
- Окна вычисляются из БД-календаря (`public_holidays` + `origin_regions`) — праздничные мосты по
  всем регионам плюс обычные Fri→Sun выходные, горизонт 6 месяцев (`fetch-window-prices.mjs`,
  `collection-windows.mjs`). Собираются обе вариации (direct + any) на точные даты окна.
- Пишется в собственную таблицу `window_prices` (+ `window_price_misses`), не в offers.
- Устойчивость: fares сбрасываются по каждому направлению, пишется `window_price_progress`.
- В coordinated mode это выполняет **tail-адаптер** (`tailPlan`) и **fast-адаптер** (`fastPlan`)
  в своих слотах.
- Legacy workflow `Carousel window prices` — 20 частей (по аэропорту), строго последовательно
  (`max-parallel: 1`), один PLAN_DATE на прогон, один catch-up-проход.

### ОТКРЫТО
- **Нет разделения «однократная ночная селекция сохранённого набора окон» ↔ «частый
  инкрементальный refresh только этого набора».** Сейчас tail на каждом проходе заново считает
  окна и план по истории, а не рефрешит зафиксированный ночью набор частями. Инкрементальный
  refresh сохранённого набора нужно спроектировать (Stage 3).
- Полный проход ~6 ч подтверждён по timeout-бюджетам legacy (части до 150 мин × 20); частый
  полный проход недопустим.

## 5. User feedback audit

### ЦЕЛЬ
- `check-flight-price-feedback.mjs` — отдельный процесс.
- Проверяет только точный билет пользователя: origin, destination, dates, return, direct/any.
- Не часть cheapest carousel и не MAIN.
- Цель — запуск каждые 30 минут, **24/7**.
- Сохраняются claim token, lease, retry и отсутствие двойной обработки.

### СЕЙЧАС (2026-09-21)
- Скрипт проверяет строго точный билет (`ticketFromFeedback`, `classifyResponse`), никогда не
  пишет prices/offers, только завершает свою leased-запись через `claim_flight_price_audit` /
  `finish_flight_price_audit`. Три попытки на запись, priority-0 idle-gate, без пользовательских
  данных в логах.
- В coordinated mode аудит выполняется как turn 0 maintenance-адаптера
  (`collection-adapters.mjs`) — по одной claimed-записи за заход, non-idempotent claim/finish без
  retry (намеренно).
- Legacy workflow `Flight price feedback audit · priority 0`: cron `47 4 * * *`, плюс жёсткое
  **ночное окно 00:00–06:00 Europe/Berlin** и idle-gate. То есть сейчас аудит ограничен ночью.

### ОТКРЫТО
- Целевой режим «каждые 30 минут, 24/7» не включён: legacy привязан к ночному окну, а в
  coordinated mode аудит идёт только в редких maintenance-слотах (раз в ~несколько часов). Снятие
  ночного окна и переход на 30-мин 24/7 — Stage 4.

## 6. Приоритеты coordinator

### ЦЕЛЬ
В каждом 30-минутном цикле приоритет:
1. user feedback audit;
2. cheapest carousel price refresh;
3. weekend/holiday price refresh;
4. MAIN;
5. TAIL;
6. maintenance и технические задачи — по их отдельному расписанию.

Все запросы используют один `TP_TOKEN` и не выполняются параллельно.

### СЕЙЧАС (2026-09-21)
- Единица планирования — 120-мин цикл со слотами fast → maintenance → main → tail → main → tail →
  reserve (см. §1). Приоритезация внутри maintenance-turns: turn 0 = feedback audit, turn 1 =
  roulette refresh, turns 2–4 = cleanup, turn 5 = metrics, turn 6 = plan cleanup.
- Явной строгой шкалы «audit > roulette refresh > weekend refresh > MAIN > TAIL» на уровне
  выбора слота нет: audit и roulette живут внутри коротких maintenance-окон, а MAIN/TAIL — в
  своих фиксированных слотах.
- Инвариант «один токен, строго последовательно» соблюдается.

### ОТКРЫТО
- Требуется привести реальный порядок к целевому: аудит и оба refresh получают гарантированный
  высокий приоритет в каждом 30-мин цикле, MAIN — следующий по приоритету крупный потребитель
  времени. Реализуется вместе со Stage 4/5 и подтверждается тестами планировщика.

## 7. Старые (legacy) workflow

### Текущее состояние гейта `COLLECTION_MODE`
Каждый legacy job имеет `if: vars.COLLECTION_MODE != 'coordinated'`. При
`COLLECTION_MODE=coordinated` они **пропускаются**:
- `Twice-daily price fetch` (`fetch-prices.yml`) — пропускается.
- `Daily cheapest offers snapshot` (`snapshot-daily-origin-cheapest.yml`) — пропускается; при этом
  этот же workflow нёс priority-0 refresh рулетки по cron `7,37 * * * *` (каждые 30 мин) — сейчас
  тоже под гейтом.
- `Carousel window prices` (`fetch-window-prices.yml`) — пропускается.
- `Flight price feedback audit · priority 0` (`check-flight-price-feedback.yml`) — пропускается
  или ограничен ночным окном.

### Правило вывода из эксплуатации
- На этом шаге legacy **не удалять**.
- Сначала перенести обязанности в coordinator и **доказать тестами**.
- Только после этого отдельным решением отключить legacy, чтобы не было двух владельцев одной
  очереди `nextout-data-collection` (Stage 7).

## 8. Этапы внедрения

Общие правила для всех этапов:
- Внешние действия (миграции, изменение переменных/секретов GitHub, включение production-сбора,
  реальные API-запросы, commit/push) — **только по отдельному разрешению владельца**.
- Ни один этап не помечается выполненным до реально сделанного и проверенного шага.

### Stage 0 — документация и read-only baseline
- **Меняется:** создан этот файл `docs/DATA-COLLECTION-RULES.md`.
- **Не меняется:** код, workflow, cron, переменные, БД, secrets, расписание, production.
- **Тесты:** не требуются (документ).
- **PASS:** файл существует, отражает текущий код и согласованную цель, помечает открытые пункты.
- **Запрещено до разрешения:** любые изменения кода/инфраструктуры; commit.

### Stage 1 — измерить фактические длительности и число запросов
- **Меняется:** только измерения/инструментальные логи в dry-run/manual, без изменения
  production-поведения.
- **Не меняется:** расписание, состав pool, production-данные.
- **Измерить:** длительность полного MAIN-прохода; полезное MAIN-время в сессии; длительность и
  число API-запросов ночной селекции и refresh рулетки (direct/any, число origins/билетов);
  длительность полного weekend/holiday прохода и объём сохранённого набора.
