## МИГРАЦИИ
Миграции лежат в `migrations/` в корне репозитория. Новые именуются меткой времени в формате
supabase CLI: `YYYYMMDDHHMMSS_short_name.sql`, например `20260725143000_add_source_column.sql`.

Числовая нумерация не возобновляется. Номера 0001-0003 уже заняты, переиспользовать их нельзя.
Эта база общая с другой кодовой базой, поэтому номера миграций идут одной сквозной
последовательностью — номер, занятый там, здесь не свободен. Метка времени даёт сквозной
порядок поверх обеих кодовых баз.

Исторические файлы с числовыми префиксами оставлены как есть и не переименовываются: они уже
применены, а при сортировке по имени `0001` идёт раньше `2026…`, так что хронология не нарушается.

Миграции применяются вручную через SQL Editor. Каждая миграция обязана быть идемпотентной
(`if not exists`, `drop … if exists` перед `create`) — применённое состояние базы из
репозитория не восстанавливается, поэтому любую миграцию должно быть безопасно выполнить
повторно.

Каждая миграция заканчивается `notify pgrst, 'reload schema';`. Без этого PostgREST продолжает
работать со старым кэшем схемы и отвергает новую колонку как неизвестную — запись падает с
`PGRST204`, хотя в самой базе колонка уже есть.
